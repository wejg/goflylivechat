# 聊天并发压测

在项目根目录执行，需要 Node.js 22+（包含原生 `WebSocket`）及正在运行的 Docker：

```sh
node tests/load/run.mjs
```

默认先进行 10、50 访客的两段预热（各 10 秒），再让 **100 个访客 + 5 个不同客服保持 WebSocket 连接，持续 600 秒**。每 5 秒同时发送 100 条访客消息、5 条客服回复，并交错执行消息历史查询、未读汇总查询和已读确认。每个虚拟客户端使用不同的模拟来源 IP；仅独立压测网络的网关被配置为可信代理，业务限流保持原样，并另行验证同 IP 连续发送会被拒绝。

脚本在当前工作区构建独立镜像，创建临时数据库、应用容器及网络。应用与数据库分别限制为 2 CPU / 512 MiB，应用仅映射至随机本机端口。数据库由 `import.sql` 初始化，仅在临时库中创建测试用户和消息。结束时移除本轮容器、匿名卷、网络和镜像标签，不连接现有应用或数据库。

测试覆盖：

- HTTP 状态与业务返回码、数据库保存的消息 ID。
- WebSocket 实际收取、接收人、方向、消息 ID、重复及遗漏。
- 并发新消息与已读确认后的未读数量；按消息 ID 确认可见范围。
- 客服和访客重连、客服重新登录、应用重启后的未读恢复及继续收发。
- 最终逐条核对 SQL 消息内容、客服、访客、方向、已读状态。
- 请求及实时消息延迟分位数、容器 CPU/内存、数据库连接情况。

结果写入 `reports/loadtest-<时间与随机标识>/result.json`；同目录保存构建与脱敏后的应用日志，以及最终核对前的 SQL 消息行快照。单次请求或消息校验失败会计入错误并继续运行至阶段截止时间；初始化失败仍立即停止。`phaseFailures` 和每个检查点的 `status` 记录失败阶段。`steadyOutcome` 单独记录持续负载结果，`status` 包含恢复检查，因此持续负载通过、连接关闭失败时整体仍以非零状态退出。`closeCompletionTimeouts` 记录连接关闭超过 5 秒的客户端；检查点分别记录 OPEN 和 CLOSING 连接，不将它们混算为活跃连接。

短程预检及指定输出位置：

```sh
LOADTEST_SECONDS=5 node tests/load/run.mjs
LOADTEST_OUTPUT=reports/my-loadtest node tests/load/run.mjs
```

`LOADTEST_SECONDS` 支持 5–3600 秒；只改变 100 访客阶段，预热和恢复检查仍执行。`Ctrl-C` 请求停止，当前操作结束后清理本轮资源。若进程被强制杀死，需按本轮唯一的 `gofly-load-<runId>` 名称清理残留资源。

这是协议级负载，不包含 100 个浏览器的 DOM 渲染。此固定负载用于验证稳定性和消息正确性，不能作为生产服务器最大容量结论。构建使用当前工作区（包括未提交改动），JSON 记录提交号、Go 工作区差异哈希及镜像 ID。

固定目标时刻的发送节拍会在前一轮变慢后追赶发送，可能触发原有单 IP 限流；报告中的发送失败需结合业务拒绝与传输错误理解。`messageAudit.savedWithoutAcknowledgement` 表示已经入库但发送未得到成功响应的行数；此时整库核对失败，不能仅用投递 `lost=0` 判断发送成功。
