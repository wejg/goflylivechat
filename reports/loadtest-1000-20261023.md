# 1000 访客并发聊天压测（2026-10-23）

结论：当前源码在本轮本地 Docker 环境、应用和数据库各 2 CPU / 512 MiB 条件下，未通过 1000 访客集中向 1 名客服发消息的负载测试。不能按此结果承诺稳定承载 1000 人；也不能将本地 Docker 端口转发链路的连接重置直接归因为业务代码缺陷或生产环境容量。

## 测试范围

- 源码提交：`dfd0aadf56302f1748a4baddd79e346768980ddb`；构建时 Go、模块和 Dockerfile 无工作区差异。
- Docker 引擎可用资源：10 CPU、约 7.75 GiB；应用与数据库各限制为 2 CPU / 512 MiB。
- 1000 个不同模拟来源 IP 的访客、1 个客服，保持 WebSocket；原有限流不变。
- 每轮 1000 条访客消息同时发送，客服每轮回复 1 名访客；同时查询未读、历史并确认部分已读。每轮完成后等待 5 秒，不追赶积压。
- 对成功响应的每条消息核验持久化 ID、双方身份、方向、客服归属、投递次数、数据库内容及已读状态。
- 测试是协议级客户端，未打开 1000 个浏览器，也未模拟客服每轮回复全部 1000 名访客。
- 使用全新临时应用、数据库、网络、随机本机端口。未访问现有服务或生产数据库，未修改业务源码及限流。

## 两轮结果

| 场景 | 实测结果 |
| --- | --- |
| 集中建连短程预检 | 10 人、50 人预热通过；建立剩余 950 个连接时发生 WebSocket 握手失败，未进入 1000 人持续阶段。`load_visitor_323` 是首个报错客户端标识，不代表最大在线容量。 |
| 每批 25 人、批间隔 100ms 建连 | 成功建立 1001 个 WebSocket；随后完成约 60 秒的 1000 访客消息负载，持续阶段失败。 |

持续阶段：

| 指标 | 结果 |
| --- | ---: |
| 实际持续时间 | 59.999 秒 |
| 消息尝试 | 7,007 |

持续阶段 3299 次访客发送、3 次客服发送、562 次已读确认请求失败，错误均为 `connect ECONNRESET 127.0.0.1:<临时端口>`；未收到 HTTP/业务返回码，不能解释为业务限流拒绝。容器未记录 OOMKilled，应用未自动重启。资源采样显示触及内存上限，但不能据此认定 OOM 杀进程是根因。

## 消息和恢复核对

全流程（包含预热、持续、重连及手动重启）共尝试 9134 条消息，4668 条获成功确认；数据库也为 4668 行。成功确认消息的 4677 次预期投递均收到，未发现丢失、重复、身份/归属错误或已落库却无成功响应的消息；SQL 内容、ID、方向和已读状态核对通过。

这只说明成功确认部分一致，不能用它抵消 4466 条消息请求失败，也不能将成功消息的延迟分位数解释为全部请求的体验。

重连及重新登录保留未读状态，但恢复后发送仍有失败。手动重启隔离应用后，未读状态保留且重新建立 1001 条连接；新流量再次失败，并增加 98 次异常关闭。连接关闭超过 5 秒的记录为 0。全流程合计 786 次异常关闭，不能与持续阶段的 688 次混用。

## 判断与边界

本轮已复现“1000 人并发时连接不稳定、发送大量失败、延迟上升”。请求涉及宿主机客户端、Docker 发布端口、应用、数据库等多层，尚未在容器内部直连或生产同规格 Linux 环境对照，因此暂不确定连接重置的具体责任层。下一步应先绕过 Docker Desktop 发布端口进行对照，并采集内存分配及连接队列证据，再决定优化位置。

没有继续做 10 分钟耐久测试：60 秒内已经明显失败，当前数据足以否定本轮配置下的稳定性验收。没有修改、部署业务代码，没有做生产环境、App 会话鉴权模式或浏览器渲染性能测试；测试脚本使用传统访客接口和预置访客数据。
