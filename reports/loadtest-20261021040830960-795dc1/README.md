**消息和数据库核对**

包括预热与恢复，共尝试发送 12,951 条，取得成功响应 12,683 条。对这些确认成功的消息，应有 13,301 次 WebSocket 投递，实际收取 13,301 次，未发现漏收、重复投递或消息 ID/方向/接收人校验错误。

最终临时库有 12,745 行消息，其中 **62 条对应没有取得成功响应的发送尝试**。因此 268 次发送失败需要分开理解：其中已有 62 行消息落库，但客户端没有得到成功结果；其余发送尝试与库中行数相差 206，尚未完成全部缺失对应关系的逐条核对。不能把后 62 条直接称为丢消息；如果客户端直接重试，存在重复发送风险。

数据库行数与客户端确认成功数不符，脚本将全量一致性核对判为失败，并在逐行所属、内容与状态核对前停止。`lost=0`、`duplicates=0` 指投递记录，不能解释为整库一致性已经通过。该轮没有保留完整 SQL 行快照，只保留汇总、日志和检查点；脚本已补充失败前保存 SQL 行快照，供后续复测定位。

**测试边界和结果解释**

- Docker VM 为 8 CPU、约 7.75 GiB 内存；应用、MariaDB 分别配置 2 CPU / 512 MiB。Node.js v26.8.1，Docker 29.8.0，MariaDB 10.11。容器最终 OOM 标志为 false，持续阶段未发生 WebSocket 意外断线。
- 每 5 秒以固定目标时刻发起 100 条访客消息、5 条客服回复，并发执行部分已读确认和历史查询。每条访客新消息还触发所属客服的未读汇总查询。
- 单客户端使用独立模拟来源 IP，仅临时网络网关被配置为可信代理；业务的单 IP 发送限流保持原样。已捕获的发送失败样例包含“发送频率过快”。请求超过 5 秒节拍后，脚本会追赶原定发送时刻，形成短时密集发送；这会与原有限流相互影响。因此不能把所有拒绝都解释为服务端数据损坏，或据此断言服务器无法承受正常每人 5 秒一条的负载。
- 错误文本只保存前 30 条，重复限流样例占满了该空间，未保留全部后续请求失败的具体原因。各端点失败总数可靠，但尚不能精确拆分每次限流、超时和连接错误；62 条无成功响应的落库消息，其具体响应失败原因仍需复测定位。
- Docker CPU 原始采样存在超过容器配额、甚至宿主核数的异常尖峰，因此未用其判断 CPU 瓶颈或容量。完整原始采样保留在 JSON 中。
- 这是 HTTP / WebSocket 协议测试，未运行 100 个真实浏览器，也未验证页面切换、DOM 渲染或生产环境极限容量。
