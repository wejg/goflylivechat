# 线上卡顿与内存分析（2026-10-23）

## 结论

当前版本已解除同 IP 下不同访客互相限流，但本次 1000 会话突发负载仍未通过稳定性验收。已确认长请求积压、752 次异常 WebSocket 关闭及明显内存增长；尚不能将卡顿精确归因到某一个函数，也没有证据确认持续内存泄漏。

全程没有重启、重新部署或强制 GC。压测客户端于 13:19:09 结束，服务端部分请求继续运行。

## 消息核对

本轮使用原有 1000 个测试身份，消息标记 LT20261023131751，目标为真实 agent 客服。

- 共实际尝试 4000 条，客户端成功确认 3016 条。
- 最终数据库查到 3110 行，全部属于 agent、方向为 visitor，覆盖 1000 个不同访客；幂等键无重复。
- 3016 条成功确认的 ID 全部与数据库一致。
- 另有 94 条虽然客户端没有成功确认，服务端仍完成了保存。不能把 984 次客户端失败全部计为数据库未保存，也不能无幂等键地盲目重发。
- WebSocket 非预期关闭共 752 次，均为客户端读到 1006 / unexpected EOF。
- 本轮没有建立额外的客服观察连接，避免顶掉用户后台连接；没有自动模拟客服回复，因此不能声称已验证 1000 会话全量双向投递。

## 源码中需要优先验证的承压路径

1. ws/ws.go 的共享消息通道容量为 256，由单个 WsServerBackend 顺序处理。enqueueMessage 采用非阻塞写入；满时返回 false，ws/visitor.go 随即关闭访客连接。1000 个客户端同步发送心跳时存在集中溢出风险，与大量断线现象相符。但当前缺少队列溢出计数，不能断言 752 次全部由此造成。
2. 每个 App 心跳在访客读取、后台处理和 pong 写入路径都涉及数据库会话检查。近同时建立的会话还会近同时触发后台租约刷新，对数据库及 App API 产生额外突发访问。
3. ws/ws.go WriteTo 先等单连接互斥锁，取得锁后才设置 10 秒写超时。这个超时不约束等锁时间。访客上线、离线、消息推送均可能向同一客服连接写入；如果写入变慢，多个 HTTP 请求可能同时等待该连接，积压会带来额外内存占用。需要阻塞/互斥锁及 goroutine 采样验证其实际贡献。

不能仅因内存没有马上回到冷启动的 8.5 MiB 就认定泄漏。无重启情况下明显回落说明大部分内存可回收；剩余占用可能包含正常运行时、连接池及缓存，但未取得 heap/goroutine profile，不能排除较小的长期泄漏。

## 后续验证顺序

先在受控环境补充队列溢出计数、Go heap/goroutine/block/mutex 采样，定位断线和长请求等待，再修复已验证的瓶颈。恢复验证应按 100、300、500、1000 逐级推进，并分别测试错峰心跳与同步心跳，观察空闲后的存活堆和 goroutine 是否逐轮累积。不建议当前直接在真实服务器继续 1000 人突发负载。
